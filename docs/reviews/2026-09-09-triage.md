## Round two: the 2026-09-10 fix verification

The reviewer re-checked the fixes (`docs/reviews/2026-09-10-fix-verification.md`) and parked findings 3 and 7 as partial, with four sub-items. All four are correct, none is a false positive, and all four are fixed:

| Item | Verdict | Fix |
|---|---|---|
| A. Spend depth trusted one view's reported height (finding 7) | Correct. A valid signature authenticates the transaction, not its inclusion; `spend_confs` was `tip - claimed_height + 1` from a single history entry. | New `ChainBackend::tx_confirmations_final` (single view: as before; the multi-view pool: min over the integrity quorum). `classify_leg` and the block-scan path cap the height-derived depth by that read (`final_depth`); an unreadable depth is 0. Unit test: the same signed spend at a claimed height of 95 reads 0 deep when the quorum says 0, 3 when it says 3, never deeper than the claim. A view that cannot see the transaction at all (a Core node without `txindex` next to Electrum views) abstains from the finality read instead of voting 0, so a blind node cannot veto what the indexed views see; the tier-L block scan keeps its own node's height when no view can answer. |
| B. The v1 checker accepted the wrong branch's key (finding 7) | Correct. The HTLC pushes both key hashes; the check accepted either for either branch. | The OP_IF selector item picks the branch, and the pubkey must hash to that branch's key (`[redeem, refund]` in script order). A refund must also satisfy CLTV (nLockTime ≥ T, same unit, non-final sequence); the v2 refund leaf gets the same CLTV check. Unit tests: refund shape signed by the redeem key, redeem shape signed by the refund key, refund with nLockTime 0 or a final sequence all read as not authentic. |
| C. Coin-removal guard read `coin_id`, records carry `asset` (finding 3) | Correct. `ChainRef` serializes under the v1 wire key `asset`; the guard never matched a real record, and the test invented the shape. | The guard reads `asset` (with `coin_id` accepted as a fallback) and fails closed: a daemon that cannot be listed refuses the removal instead of allowing it. The test uses the real wire shape. |
| D. Failed keep-running hand-off destroyed the window (finding 3) | Correct. A failed hand-off write returned before the detach flag; the UI's fallback destroyed the window and the exit handler stopped the daemon. | For keep-running, a failed hand-off keeps the window open, shows the error (all 26 locales), and lets the user retry; the destroy fallback remains only for the stop-and-exit path, where stopping is the intent. |

## Removed from the work list

- **History costs scale with all past swaps.** Measured against the post-#235 engine at a synthetic scale sixty times the real field database. At the field scale this is milliseconds and a few hundred kilobytes per poll on loopback. No fix.
- **Relay storage and inbox lifecycle.** Corkboard is opt-in and self-hosted; the daemon inbox is cursor-bounded and stores only own-addressed mail. Hygiene, not availability. No fix.
- **Bundle size warning.** The UI is embedded in the Tauri binary and served locally. No fix.

## Corrections to the review text

- Finding 1 / transport: `pactd_call` already ran under `spawn_blocking`; only the reprobe executed on the async runtime thread.
- Finding 4: v1 `redeem` enforces depth itself; the gap was v2-only.
- Finding 5: severity was higher than stated because the poison message survived restarts.
- Finding 9: only the two Initiator arms were affected; Participant refunds are independent of chain A.
- Regression concern: the gap also covered v2 leg A on both wallet types, not just Core leg B.
- Perf history table: measured against the post-#235 engine, so it did not describe the field stall that #235 fixed.
